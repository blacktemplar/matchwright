# AGENTS.md

This file provides guidance to AI agents when working with code in this repository.

> **Edit files only with the Edit/Write tools.** Never change files through shell scripts (`python`, `sed`, `awk`, heredocs, ...), not even for large or repetitive changes: split them into several Edit calls instead. See *Working style*.

## Commands

Verify changes by running the hooks from `.pre-commit-config.yaml` (CI runs the same ones) rather than the individual cargo commands:

```sh
prek run --all-files          # or: pre-commit run --all-files
prek run --all-files cargo-test   # a single hook
prek run --all-files --stage manual   # all hooks plus the slow ones only CI runs (wasm-test, web-e2e, gui-e2e)
```

The hooks are `cargo-fmt`, `cargo-clippy` (`-D warnings`), `cargo-clippy-wasm` (the crates that run in the browser, for `wasm32-unknown-unknown`, configured by `clippy-wasm/clippy.toml`), `cargo-test`, `cargo-doc` and `cargo-sort`. `cargo-fmt` needs **nightly** rustfmt because `rustfmt.toml` uses unstable options.

- Run a single test: `cargo test -p tournament-engine <test_name_substring>`. Integration tests live in `tournament-engine/tests/` (pick a file with `--test full_tournament`).
- Doc tests count; several public items carry runnable examples.
- WebAssembly: `tournament-engine`, `plugin-factory`, `tournament-app` and the library of `tournament-cli` (without its default feature `terminal`, i.e. `--no-default-features`) must build for and pass their tests on `wasm32-unknown-unknown` (the browser frontend runs on them). `tournament-web` and `tournament-browser` only run in a browser: their tests are `#[wasm_bindgen_test]`s in modules that only exist on wasm, and run in headless Chrome (`wasm-pack test --headless --chrome tournament-web`, likewise `tournament-browser`). The wasm tests are too slow for every commit, so the `wasm-test` hook (needs `wasm-pack`, and Chrome with chromedriver) is in the manual stage and runs in CI: `prek run --all-files --stage manual wasm-test`. Run it after changing those crates. For a single crate or file: `wasm-pack test --node tournament-engine --profile wasm-test [--test <file>]`; the profile drops debug info, without which the runner is more than twice as fast. Doc tests and the benchmark run natively only. Randomness from the system (`rand`'s `thread_rng`, `Uuid::new_v4`) is chosen by the final application on wasm (`getrandom/wasm_js`, `uuid/js`), so the libraries must not enable it in their normal dependencies.
- End-to-end tests of the pages: `e2e-harness` serves a built page and drives headless Chrome over WebDriver (`thirtyfour`, which starts chromedriver itself and downloads it if needed, or uses the one `E2E_CHROMEDRIVER` names, as CI does with the runner's), through a `Page` (`open_at`, `reload`, `leave`, tabs with `tab`/`open_tab`/`switch_to`/`close_tab`, `expect_download(name)` for a file downloaded into a directory of the test's own, `go_offline` (stops the server), `expect_kept_offline` (everything loaded is in the cache storage), `expect_installable` (Chrome's DevTools), `expect_text`/`expect_texts`/`expect`, `check_accessibility`). Each page has its crate wrapping `Page` in what an operator does there: `tournament-web-e2e` (`Terminal`, on the page built by trunk) and `tournament-gui-e2e` (`Gui`, on the page built by `dx build -p tournament-gui --release --debug-symbols false`: `run` starts at the empty list of competitions, `run_in_new_competition` in a new competition named `COMPETITION`; `new_competition`, `open_competition`, `expect_progress` (how far each competition of the list is), `import(path)`, `follow(link text)`, `add_entrant`, `choose_format`, `choose_plugin(path, label)` (a plugin of the form of the phase, by the path of its field, or one added to the list at the path), `enter(path, text)`, `toggle(label)` (a checkbox), `choose_language`, `choose_round(option text)`, `find_entrant(text)`, `click(text)`, `click_labelled(aria-label)` (also a result button: it shows "Wins" and is labelled "Alice wins"), `enter_result("3 1")`, `press(key)` (where the focus is), `expect_competitions`/`expect_open`/`expect_read_only`/`expect_entrants`/`expect_matches`/`expect_results`/`expect_finished` (the numbers of the matches with a result, whoever won)/`expect_stages`/`expect_standings`/`expect_error`/`expect_announcement`/`expect_focus(text)`/`expect_focus_in_match(number)`/`expect_disabled`/`expect_page_language`/`choose_theme`/`expect_theme`/`expect_storage_warning` (its paragraphs; headless Chrome refuses persistent storage and offers to install the page, so it shows in every test), and for the phase `expect_list`/`expect_checked` (what the browser shows checked in a set of plugins)/`expect_issues`/`expect_phase` (the summary's answers)/`expect_dialog_error`/`expect_no_dialog`). Chrome prefers English, so a page shows English unless a test chooses otherwise, and opens at a laptop's size (1280×900), where the GUI shows every column. Translated texts wrap every variable in the invisible marks U+2068/U+2069 (`e2e_harness::ISOLATION_MARKS`); `Page::expect_texts` and the `Gui`'s buttons ignore them, while `Page::expect_text` does not, so use it only for texts without variables. A terminal test is `run(async |terminal| { .. })` on a fresh page with nothing saved, through its `Terminal`: `run(line)`, `press(key)`, `leave()`, and `expect_reply`/`expect_error`/`expect_prompt`/`expect_input`/`expect_output`, which wait until the page shows what they expect and otherwise panic with what it shows; `terminal.driver` reaches everything else. A test fails as well if the page logs an error, e.g. a wasm panic, or if axe-core finds a WCAG 2.1 A/AA violation on the page at its end (axe-core is downloaded at a pinned version and cached in the user's cache directory); call `check_accessibility` for states in between. Sides of a match come from the random seed, so a GUI test must not depend on which side an entrant is on. A failed test leaves `screenshot.png` and `report.txt` (URL, page source, browser log) in `target/e2e-failures/<test file>/<test>/`, which CI uploads as the artifact `e2e-failures`. Extend `Terminal` rather than repeating WebDriver calls in tests. Test there what only the page does (input, history, URL, reloads, leaving); what a line shows belongs in the `wasm_bindgen_test`s of `tournament-web`. The tests are `#[ignore]`d, so that `cargo test --workspace` needs no browser; the manual-stage `web-e2e` hook (needs `trunk` and Chrome) builds the page and runs them, and CI runs it: `prek run --all-files --stage manual web-e2e`; the `gui-e2e` hook (needs `dx` of the version of `dioxus` in `Cargo.lock`, and Chrome) does the same for the GUI. A single one: `cargo test -p tournament-web-e2e <name> -- --ignored`, after `cd tournament-web && trunk build` (for the GUI: `-p tournament-gui-e2e` after `dx build -p tournament-gui --release --debug-symbols false`; the debug build tries to reach `dx serve` and logs an error); with `E2E_HEADED=1`, Chrome opens a window that shows what the test does, `E2E_PAUSE=<seconds>` pauses that long after each action of the `Terminal` (and in `run` also between typing the line and Enter; give a new action a pause too), and `E2E_LINGER=<seconds>` keeps the window open that long after the test (add `--test-threads=1` to watch one test after the other).
- Benchmark: `cargo bench -p tournament-engine --bench large_tournament` (criterion).
- Example: `cargo run -p tournament-engine --example run_tournament`.
- CLI: `cargo run -p tournament-cli -- [FILE]` (see `tournament-cli/README.md` for its commands).
- Web: `cd tournament-web && trunk serve` (see `tournament-web/README.md`).
- GUI: `dx serve -p tournament-gui` (add `--hot-patch` to patch Rust code into the running page); the release build is `dx build -p tournament-gui --release --debug-symbols false` (dx runs `wasm-opt` itself, but keeps debug symbols unless told), with `--base-path <path>` for a page served under a path; see `tournament-gui/README.md`.
- Profile `release-checked`: release with debug assertions and overflow checks.
- Keep `Cargo.toml` dependency lists sorted (the `cargo-sort` hook checks this). Dependency versions are declared only in the root `[workspace.dependencies]`; members use `dep.workspace = true`. `plugin-factory` and its proc-macro crate `plugin-factory-derive` are the exception on purpose: they declare everything themselves, including `version`/`edition`/`license`, so that they can be moved out of the workspace together. Don't give them workspace references, and don't let them depend on the other crates.
- `undoable-state-machine` is a git dependency (same author) that follows its `main`; `Cargo.lock` pins the commit. After pushing a change there, pick it up with `cargo update -p undoable-state-machine`.

## Architecture

The crates: `tournament-engine` (the library), `tournament-app` (what the GUI does, without any UI: a session with typed data for screens, on the engine), `tournament-gui` (the GUI, Dioxus in the browser, on `tournament-app`, with its end-to-end tests in `tournament-gui-e2e`), `tournament-browser` (what the GUI needs of the browser besides its page: IndexedDB storage, locks, channels between tabs, files), `tournament-cli` (an interactive REPL on the engine) and `tournament-web` (the CLI's command line in the browser, via wasm, with its end-to-end tests in `tournament-web-e2e`), `e2e-harness` (what both e2e crates share), plus `plugin-factory` (generic plugin axes, catalog, schemas, drafts, compatibility), which the engine builds on and which must not depend on the others. `DESIGN.md` is the authoritative design record, with the rationale and rejected alternatives for each decision. Read the relevant section before changing a mechanism. Sections marked *planned* are not implemented. Some type names in it may lag behind recent renames (e.g. ranking "criteria").

### Global constraints (from DESIGN.md, apply everywhere)

- **State changes only through logged transitions.** Progress is an `undoable-state-machine` `StateMachine<Competition, Box<dyn CompetitionTransition>>` (`CompetitionStateMachine`). Undo means replaying the remaining log from the initial state. `Competition`'s mutators are crate-internal on purpose. `undo`/`redo` are per session: an `undoable_state_machine::SessionHistory` records the entries the session appended as its actions (any kind, including a targeted undo such as `undo_match_result` and a reconfiguration) and undoes/redoes them in order with explicit undo entries; it is not persisted. Engine operations that append an action take the history (`CompetitionStateMachineExt::apply_in`, `undo_match_result`, `reconfigure_phase`); `apply_transition` appends outside any history (the seed, tests).
- **Determinism under replay.** `Transition::apply` must be a pure function of state plus the transition's own data. Randomness comes from the competition seed (`SetCompetitionSeed`); a phase format draws from `PhaseData::rng`. Ids (`MatchId`, `RankingId`) are UUIDv5s derived from content. Anything non-derivable (names, timestamps, external ids) must arrive as transition data.
- **Runtime-pluggable, third-party-open axes, built on `plugin-factory`.** Each axis is a public unsealed trait used as `Box<dyn Trait>`, declared with `#[plugin_factory::axis]` with `plugin_factory::Plugin + DynClone` as supertraits: `PhaseFormat`, `SliceRanker`, `MetricsCalculator`. Each implements `Clone` for `Box<dyn Trait>` with `dyn_clone::clone_trait_object!(Trait);`. A plugin derives `Plugin` (`#[plugin(id, label, description, declare_static, declare)]`; its schema comes from its fields, each needing `#[plugin(label = ..)]`) and registers with `#[register]` on its axis impl, which also tags it for `typetag` with its id. Facts a plugin provides/requires go through `plugin_factory::compatibility::Declaration`; the engine's own facts are in `plugins::facts`. Runtime state of a plugin (e.g. the bracket) is a `#[serde(default)] #[plugin(skip)]` field. The ranker is not an axis: a phase is always ranked by a `HierarchicalRanker` built from its list of slice rankers. A criterion like `MorePoints` implements the helper trait `RankingCriterion` (metric type + comparison), declares `declare_static = requires_metric::<Self>` and registers with `register_criterion!(MorePoints)` in place of `#[register]`, which implements `SliceRanker` by `rank_by`. Don't use closed enums, generics on entities, or `enum_dispatch`. DESIGN.md explains why generic entities fail with `typetag`.
- **A phase's plugins are the composite `PhasePlugins`** (`Configurable`: format, ranking, metrics). Facts nothing provides are handled before the transition, by `Draft::add_implied` on the draft `Competition::phase_draft` creates (it carries the crate-internal `Competition::declare_phase_context` as its context): it appends the implied plugins, i.e. for a missing fact the single fieldless plugin providing it, to the answers, and calling it again adds nothing. `Draft::build` (`&self`) builds from the answers as they are, adding nothing; whether to call `add_implied` first is the caller's choice (`Session::add_phase` does, on a clone, and summarises the resulting answers). In production, building from that draft is the only way to make `PhasePlugins` besides deserializing; code answers it with configs (`Draft::with(field, PluginConfig::of::<P>().with(..))`, `Draft::with_defaults`). Tests build plugins directly instead, see *Writing tests*. Its calculators are a `plugin_factory::schema::DependencyOrderedSet`, which keeps plugins in running order on `DependencyOrderedSet::new` and on deserialization and rejects duplicates and cycles (`DependencyOrderedSetError`); the slice rankers are an ordered `Vec`. `AddPhase::check_applicable` runs `compatibility::check`. A phase is changed after it was added by reading `Phase::config` (the plugins serialized as their config, runtime state dropped, via `plugin_factory::config::Config::of`), putting it into a draft with `Draft::with_answers`, and handing the built plugins to `CompetitionStateMachineExt::reconfigure_phase`, which appends a `LogEntryKind::Replace` of the phase's `AddPhase` with one of the same phase id. A new plugin needs only its derive and `#[register]` (a criterion `register_criterion!`); a consumer must not grow a table of plugins.
- **No untyped data bags.** Open-ended data is keyed by Rust type through `TypeMap` (`type_map.rs`). Metrics are `TypeMapValue`s, identified in-process by `TypeId`. Consumer data is stored as an annotation in a `TypeMap` field on the entity. It is written by the transition that creates the entity (`Entrant::new(id).with_annotation(..)`).
- **No personal data in the log.** The log replays as written and cannot have parts deleted, so names and other personal data stay out of it: they are kept in `People` (`tournament-app/src/people.rs`, which the CLI re-exports), keyed by `EntrantId` and saved next to the log.
- **Scores.** Points and the metrics built from them are `Score` (`score.rs`): a finite `f64` (never NaN or infinite, `-0.0` made `0.0`) with `Eq`, `Ord` and `Hash`, made with `Score::new(0.5)` (a `const fn`). An operation whose result is not finite panics.
- **Ranges of numbers in the schema.** A numeric field's `FieldKind` carries its range (`IntegerRange`, `DecimalRange`: `min`, `max`, `multiple_of`, the multiples anchored at 0). The type declares it in `FieldType::kind`, a field narrows it with `#[plugin(min = .., max = .., multiple_of = ..)]` (e.g. `min = 0` for points); the draft rejects a number out of range (`ConfigError::OutOfRange`) and prompters ask within it.

### Persistence

- Two paths: a `Competition` snapshot, and the transition log (the CLI saves the log as JSON, as `{"log": .., "people": ..}`; the app crate stores each log entry and each person as a JSON record of its own; neither saves the session's undo history). Deserializing the log rebuilds the state by replay. A log that doesn't replay fails to load.
- Trait objects serialize via `typetag` with **adjacent tagging** (`#[typetag::serde(tag = "type", content = "value")]`). Internal tagging breaks non-self-describing formats like postcard, so don't switch to it. Tests exercise both postcard and serde_json.
- **Tags are persistence contracts.** Every `CompetitionTransition` impl has an explicit namespaced tag (e.g. `#[typetag::serde(name = "tournament_engine::...")]`), pinned in tests. A plugin's tag is its `PluginType::ID` (namespaced, e.g. `tournament_engine::points`), pinned in `tests/transition_log_serialization.rs`. New transitions/plugins/metrics/annotations need an explicit tag; never change an existing one.
- `IdMap` (`map.rs`) and `TypeMap` wrap `IndexMap` and serialize as plain sequences in insertion order. Code may rely on that order (e.g. match numbers are derived from insertion index).

### Engine data flow

`Competition` → `Phase` (holding its `PhaseFormat`, ranker, metrics calculators, `matches`, `byes`, `rankings`) → `Match` / `Bye` / `Ranking`. On `StartCompetition` and after every reported result the phase format schedules a `Schedule` of matches and byes (`create_new_matches(&PhaseData)`); a bye is final when scheduled, so each calculator's `update_after_bye` runs right away, followed by a re-rank. On `ReportMatchResult` the match is appended to `Ranking::played_matches` of its rankings, each `MetricsCalculator` updates metrics incrementally (`update_after_match_result`, which gets the *old* metrics of the calculators that ran before it), then the ranker re-sorts. This is the hot path, so `rank_by` looks up each ranking's metric once per sort instead of per comparison.

### App

`tournament-app` is what the GUI (see `FRONTEND_PLAN.md`) does without any UI, so that it is tested natively and in wasm like the engine; it must not depend on a UI crate or on the CLI. `session.rs`'s `Session` runs one competition for an operator: each action (`add_entrant`, `add_phase` from a `Draft`, `phase_draft(format)` with the format's defaults, `edit_phase`, `start`, `report` (returning the match's row with what it led to), `report_entered("3 1")` (a match's number and `1`/`X`/`2`), `undo_report` by `MatchId`, `undo`/`redo`, which return the `view::Action` they walked through, kept by the session as it was done) turns into transitions through its `SessionHistory`, and is refused with a typed error per action (`error.rs`; engine errors are recognized by downcasting the `TransitionError`, anything unknown is `Rejected`), each a `Message` that says a `Text` (a Fluent key and its variables). Translation (`i18n.rs`, Fluent): a `Translator` of a `Language` holds the app's messages (`locales/<lang>/app.ftl`, English saying what the error's `Display` says) and a consumer's, handed over as `Resources` (`fn(Language) -> &'static str`, an exhaustive `match`); a message missing in the language comes from English. Plugins are translated in `locales/<lang>/plugins.ftl` as attributes of `plugin-<id with :: as ->` (`PluginText`: `.label`, `.description`, `.column`, `.field-<name>`, `.field-<name>-description`, and a format's `.stage-<key>` with the stage's numbers as variables, said by `Translator::stage` of a `view::StageName`), English being the plugin's code; a new plugin of the engine needs its German there (a test checks every plugin is, and nothing else; a format naming stages is listed in its `stages` with one stage of each key). `i18n::check` is the test of a consumer's resources (parse, no key twice, every language has English's messages and attributes). It hands out plain data for screens (`view.rs`: entrant rows with an `Option` name, `rounds`/`round` with match rows numbered as the CLI does, `playable` (the open matches none of whose entrants has one of an earlier round open), `NameSearch` (finds entrants and match rows by part of a name, whatever the case and the accents), `standings` with the metric columns, `actions` for what can be done now). A phase is configured through `form.rs`'s `PhaseForm` (`Session::phase_form` for a new phase, `phase_form_to_edit` for the one played), the GUI counterpart of the CLI's questionnaire: `view()` is a `FormView` generated from the draft's schema (each `FormField` by `Path`, with an `Input` by kind: numbers with their range and a hint, a plugin with its options, recommended first, a list with its items, the plugins it implies and those that can be added; the issues of the draft with the implied plugins added, at the field or item where they are fixed, as `Text`s), and its changes (`set_bool`, `enter` of a typed number, which keeps what was not taken with why, `choose`, `add`, `remove`, `move_up`/`move_down`, `answer_optional`) answer every field after the changed one in schema order still answered as offered by what it offers after the change, so that another format brings its recommendations, while a field before it never follows (removing a metric must not silently drop the criterion needing it; an issue shows it); `draft()` goes to `add_phase`/`edit_phase`. The fields of a phase itself are translated by the attributes of the message `phase` in `plugins.ftl` (`Translator::field_label`), and a `Text` may carry a plugin's label as a variable (`Arg::Plugin`), translated when said. Storage (`storage.rs`) is the async `Storage` trait (`fn .. -> impl Future`, not dyn-compatible, futures need not be `Send`): `list` (each `Listing` with the `Progress` of its latest save: changes update it only if they `reach_end` of the stored log), `read(key, first_entry)` (the log from a position on, and every person) and `write` of `Changes`, i.e. the log entries appended since the last save (written at their position, so writing again or out of order is harmless) and the people changed, each a JSON record. A save is `unsaved_changes()`, the write, then `mark_saved(&changes)`, so a GUI holds no borrow of the session across the write (`Session::save` does all three); a failed write leaves the changes for the next save. A session with nothing unsaved catches up with what another one saved by appending the stored entries after its own log (`StateMachine::apply` of each entry, no replay but for undo/replace entries) and taking the people as stored, the same way apart: `next_entry()`, the read from there, then `catch_up_with(&stored, first_entry)` (`Session::catch_up` does both). `MemoryStorage` finishes every future at once; tests poll them once with a no-op waker (`now` in `session/tests.rs`). A competition is moved as a file (`file.rs`): JSON `{"name", "log", "people"}`, which is what the CLI saves plus the name, so each opens the other's files; `Session::export` writes it, `Session::import(file, name)` makes a new competition of it under a new key with nothing saved yet, and `Stored::export` writes what is stored as it is, so that a log that no longer replays can still be exported.

### GUI

`tournament-gui` is a Dioxus 0.7 app (`Dioxus.toml`, `index.html` with `lang`, plain CSS in `assets/style.css` through `asset!()`), built by `dx`. Its components only lay out what `Session` hands out (`actions()`, `entrants()`, `rounds()`/`round(n)`, `standings()`) and show the `Text` of a refused action's error in a `role="alert"`; logic belongs in `tournament-app`, where it is tested natively and in wasm. Every text on the screen goes through the `Translator` in `Ctx`: `tr.get("key")`, `t!(tr, "key", name = value)` for variables, `tr.plugin(id, PluginText::Label, english)` for plugins; its messages are `locales/<lang>/gui.ftl` (`i18n.rs`, whose test runs `i18n::check` on them). The language is the one chosen last (local storage), else the browser's; `<html lang>` follows it. The phase (`phase.rs`) is laid out from the `FormView` of a `PhaseForm` held in a signal: the form of a new phase in place, and once added a summary with a button opening a dialog that edits it (`Ctx::try_act`, so the dialog shows a refusal itself). The layout (DESIGN.md, *Layout*): one bar on top (the `Header`, followed by the competition's actions as a sibling the page's grid puts into the same row), cards in columns where there is room (`.columns`; below 60rem buttons choose the column shown, the other hidden by CSS only), names never cut, the language and the colours (`theme.rs`: the system's, light or dark, as `<html data-theme>`) in the footer. Colours only through the tokens at the top of `style.css`, each `light-dark(light, dark)`, onto which the components' theme variables are mapped; a new colour is a new token with both values, meeting WCAG AA in both. After the start (`play.rs`) one list of matches is shown, a round (chosen by a select with previous/next buttons) or those playable now, each match a card of the two sides around its number with each side's button below its name, with a field taking a typed result; a result button moves the focus on to the next match without one (or the list's heading) through the `onmounted` handle of `use_focus`, in components that exist only while their buttons do. What an action did is shown in the live region `.announcement` (`announcement.rs`'s `Announcement`, kept as data and said when shown; `Ctx::announce` after a successful `act`, which clears it). Widgets HTML has no good form of come from the Dioxus team's components in `src/components/` (copied by `dx components add`, each with its `style.css`, whose class names `css_module` hashes, so their styles are changed there, each change marked; on `dioxus-primitives`, a git dependency pinned in `Cargo.lock`): `select` (a plugin's choice, with descriptions in its options; its trigger has an id and is named by `labelled_by` plus its value) and `dialog`. The page (`main.rs`) has one `Header` for every screen (so that its elements stay while screens change; the competition shown names it through `Page::shown`), and shows the list of competitions (`competitions.rs`: open, export, new, import from a file) or the competition the URL names after its `#` (`competition.rs`). State every screen shares is `Page` (signals of the storage, the translator, the last error, whether the browser persists storage); that of the competition open is `Ctx` (the session, the lock, and the signals of `Page` it needs). Storage is `tournament-browser`'s `IndexedDb`. One tab at a time changes a competition: the one holding its Web Lock (`tournament-gui.competition.<key>`); another shows it read-only (`Ctx::actions()` is all false, `Ctx::changes()` false), catches up whenever the writer posts its key on the `BroadcastChannel` `tournament-gui.saved` after a save, and takes over when the lock is released. `Ctx::act` runs an action and then saves take/write/mark in a task that outlives the screen and holds the lock until written, without holding the session across the write, and returns the action's value if it was done. Opening a competition asks the browser to persist storage; a refusal shows a warning (`notices.rs`) offering to export, to install the page (`install.rs`, while the browser offers it; persistence is asked for again once installed) and not to show it again (local storage). The page is a PWA: `public/` (copied by `dx` next to `index.html`, so its URLs are relative) holds the manifest, icons (the PNGs rendered from `icon.svg`), the service worker `sw.js` (assets from the cache once kept, everything else from the network, the cache when that fails; a changed page drops the old assets) and `pwa.js`, which registers it, hands it what the first visit loaded before it took over, and keeps Chromium's `beforeinstallprompt` as `window.tournamentInstallPrompt` for `install.rs`. Its tests are the e2e tests of `tournament-gui-e2e`; it is linted for wasm by `cargo-clippy-wasm`. Accessibility is WCAG 2.1 AA: semantic HTML (labels, `th scope`, landmarks, buttons named by what they do, e.g. "Alice wins", `aria-label` where the text alone is ambiguous, e.g. "Remove Alice").

### Browser

`tournament-browser` is what the GUI needs of the browser besides its page, each testable in headless Chrome: `indexed_db.rs`'s `IndexedDb` is the app's `Storage` on IndexedDB (on the crate `idb`; stores `competitions`, `entries` under `[key, position]`, `people` under `[key, entrant]`, each record a JSON text; a write is one transaction that refuses changes leaving a gap in the log, run on wasm-bindgen-futures' executor since the transaction stays active only in the microtasks after a request's result); `lock.rs`'s `try_lock`/`lock` take a Web Lock (bound by hand: web-sys has it only behind `web_sys_unstable_apis`), held until the `Lock` is dropped; `channel.rs` has `Events` (a target's events as a `Stream`) and `Broadcast` (a `BroadcastChannel`); `persistence::persist` asks the browser to keep what is stored; `file::download` has it download a text as a file.

### Web

`tournament-web/src/lib.rs` holds what is testable: `LocalStorage` (the CLI's `Storage` on the browser's local storage) and `Shell`, which runs a line against a `Session` and returns its `Reply`s (clap's help as output, its errors as errors; `exit` starts a new competition). For `add-phase` without a format and `edit-phase`, the shell keeps the `fill_async` future of the phase's draft and resumes it with every line, which `questions.rs`'s `LinePrompter` takes as the answer to the question waiting (polled with a no-op waker: only a line handed over by the shell lets it continue). `main.rs` only wires the page of `index.html` up to it (input with history, output, prompt, the competition named after `#` in the URL, a warning before leaving with unsaved changes). It is a thin text layer on purpose: the planned Rust GUI is a separate rewrite, not built on it.

### CLI

`tournament-cli/src/lib.rs` holds everything testable. `command.rs` parses a line into a `Command`, and `session.rs` executes it against the state machine and handles save/load through a `Storage` (`storage.rs`: bytes under a name; `FileStorage` writes atomically via a temp file, tests use `MemoryStorage`). `questionnaire.rs` is the generic, schema-driven questionnaire: it fills a `Draft` of any `Configurable` through a `Prompter` (`Terminal` asks via `inquire`, `AcceptDefaults` takes every offered answer) and knows no plugin. The logic is the async `fill_async` over an `AsyncPrompter`, which may wait for answers (the web's line prompter); every `Prompter` answers right away and is an `AsyncPrompter` by a blanket impl, so the synchronous `fill` polls `fill_async` once and can never be left pending (no executor). An operator stopping the questions is `questionnaire::Error::Cancelled`, whatever the prompter; the CLI fills `Competition::phase_draft` with it, and for `edit-phase` the draft `Session::phase_draft_to_edit` returns, which it hands to `Session::edit_phase`. `add-phase <FORMAT> [FIELD=VALUE]...` looks the format up in the catalog by its label or id; everything else is what the format `recommends`, so the CLI keeps no table of plugins. Its `people` are those of `tournament-app`. `main.rs` only does terminal I/O (rustyline). The default feature `terminal` gates everything that only works at a terminal (`inquire`, `rustyline`, `Terminal`, the binary), so that the library builds for wasm without it. The engine knows nothing about display, except that a `MetricsCalculator` may offer a `MetricColumn` (a header plus the `Display` of its metric) and a `PhaseFormat` may name the stage of a match or bye from its annotations (`PhaseFormat::stage`, a `Stage`: a key, its numbers, and its English name as `Display`); the CLI's standings show the column of every calculator of the phase that offers one, in running order, and its match list shows the stages (those of byes only where their round has several, as the app's `ByeRow::stage`).

## Writing tests

- **A test names only what it is about.** Build test data with a builder and leave everything else to its defaults, so that a reader sees at a glance what matters to the test. Prefer a builder over a helper function with positional parameters: a helper forces every caller to spell out every part, and hides which of them the test cares about. Don't add a helper that only wraps a builder with fixed arguments; inline the builder chain. When a test needs data no builder offers yet, extend the builder (with a sensible default) rather than writing a helper.
- **Builders of the engine**, behind the `test-util` feature: `PhasePluginsBuilder` builds `PhasePlugins` (defaults: a round robin, an empty ranking, no metrics), `PhaseBuilder` a standalone `Phase` for unit tests of plugins (the same plugin defaults, plus `add_players`). Plugins with fields have constructors behind the same feature (`PointsCalculator::new(..)`, `SingleElimination::new()`, ...); a new plugin with fields gets one under `#[cfg(feature = "test-util")]`, and an ungated doc comment must not link to it. The engine's own tests, benchmarks and examples get the feature through a dev-dependency on the crate itself.
- **Every test also runs in WebAssembly.** The wasm test runner only runs `#[wasm_bindgen_test]`, and silently skips a plain `#[test]`. So each test module (and integration test file) of a crate that builds for wasm imports `#[cfg(target_arch = "wasm32")] use wasm_bindgen_test::wasm_bindgen_test as test;`, which makes its `#[test]`s run there; the `cargo-clippy-wasm` hook rejects a plain `#[test]` (`disallowed-macros`). A nested module with `use super::*;` needs the import itself, since the glob would make `test` ambiguous. A test that cannot work in wasm (e.g. one using `catch_unwind`: wasm aborts on a panic) gets `#[cfg_attr(target_arch = "wasm32", ignore = "<why>")]`.
- **Configs only where configuration is tested**: drafts (`Competition::phase_draft`, `Draft::with`, `PluginConfig`) belong in tests of configuration, of implied plugins, or of a consumer's configuring (the CLI's `Session::add_phase` takes a draft).

## Working style

- Prefer tools and commands that are already allowed, plus the normal Read/Edit/Write tools, over anything that triggers a new permission prompt. For example, edit files with the Edit tool rather than `sed` or a `python` script, and run the existing commands as they are rather than wrapping them in new pipelines. Only ask for a new permission when there's no reasonable alternative.

## Conventions

- The user prefers invariants enforced by types/the compiler over runtime checks or self-reported plugin facts, and is cautious about costs on the result-reporting hot path.
- Plugin labels and descriptions follow the guidelines in the docs of `tournament_engine::plugins` ("Labelling a plugin"), checked in part by a test there. The answer a field offers is `#[plugin(default ..)]`; `#[serde(default)]` only governs loading and offers nothing.
- Doc comments follow KISS: say what a public item does and everything a caller needs in order to use it (contract, panics, errors, ordering guarantees), nothing more. No historical rationale, no comparison with rejected alternatives — that belongs in `DESIGN.md`. Where a *maintainer* needs the reasoning, put it in a plain `//` comment next to the code instead of in the rustdoc.
